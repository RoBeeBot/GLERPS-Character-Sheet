- Mejor UI
- regex o bloqueo de cosas
- agregar placeholders
- agregar una guia rapida de como funciona
- idiomas o aclaraciones
- app de dados
- agregar total de puntos en cada cosa
- agregar valores de cada punto por ejemplo de ST equivalente a los puntos totales
- Orden alfabetico de cosas agregadas
- agregarle filtros para mejor navegacion
- boton de deshacer para volver atras
- Se le puede poner categoria a las habilidades o desventajas para separalas de las demas o que tengan un color para diferenciarlas asi haciendolo mas intuitivo y no tener que escribir quirk: mi quirk, habilidad: mi habilidad



==================================================

# 40.5 UX, PRODUCT & USABILITY REQUIREMENTS

==================================================

Además de la arquitectura, dominio, reglas y testing definidos anteriormente, la aplicación debe tener una experiencia de usuario profesional.

IMPORTANTE:

Estas funcionalidades NO deben implementarse todas inmediatamente.

Deben analizarse durante DISCOVERY y clasificarse como:

* MVP
* V1
* FUTURE

No implementar funcionalidades futuras antes de que sean necesarias.

La UX debe construirse sobre el dominio y application layer existentes.

La UI NO debe implementar reglas del sistema.

==================================================

# 40.5.1 UI / VISUAL DESIGN

==================================================

La interfaz debe ser:

* clara;
* moderna;
* consistente;
* intuitiva;
* responsive;
* accesible;
* rápida;
* visualmente jerárquica.

Evitar interfaces que parezcan formularios administrativos genéricos.

El usuario debe poder entender:

* dónde está;
* qué está editando;
* cuánto lleva gastado;
* qué errores tiene;
* qué puede hacer;
* qué debe hacer después.

Utilizar componentes reutilizables y un sistema visual consistente.

No crear estilos diferentes para cada feature sin una razón.

==================================================

# 40.5.2 CONTENT TYPES

==================================================

Los elementos del sistema deben diferenciarse visualmente por tipo.

Ejemplos:

* Advantage
* Disadvantage
* Skill
* Weapon
* Armor
* Equipment
* Hatsu
* Creation
* Quirk
* Language
* Cultural Familiarity

No obligar al usuario a escribir manualmente:

"Skill: My Skill"

o:

"Quirk: My Quirk"

El sistema debe conocer el tipo del contenido.

Ejemplo conceptual:

Content:

{
type: "skill",
category: "combat",
name: "Broadsword"
}

La UI puede mostrar:

[SKILL] Broadsword

==================================================

# 40.5.3 CATEGORIES

==================================================

Los contenidos pueden tener categorías.

Ejemplos:

Skills:

* Combat
* Social
* Knowledge
* Physical
* Mental
* Crafting
* Survival

Advantages:

* Combat
* Social
* Physical
* Mental
* Supernatural

Creations:

* Creature
* Weapon
* Armor
* Tool
* Structure
* Trap
* Mobility
* Support

Las categorías deben ser datos/configuración siempre que sea posible.

No hardcodear categorías dentro de componentes.

==================================================

# 40.5.4 TAG SYSTEM

==================================================

Implementar un sistema de tags extensible.

Ejemplo:

Broadsword:

[SKILL] [COMBAT] [DX] [MELEE]

Snake:

[CREATION] [CREATURE] [SUPPORT]

Combat Reflexes:

[ADVANTAGE] [COMBAT]

Los tags deben poder utilizarse para:

* búsqueda;
* filtrado;
* agrupamiento;
* ordenamiento;
* visualización.

Los tags NO deben reemplazar las categorías ni el content type.

Separar conceptualmente:

Content Type

→ Category

→ Tags

==================================================

# 40.5.5 SEARCH

==================================================

Implementar eventualmente una búsqueda global.

Debe poder buscar:

* nombre;
* categoría;
* tags;
* atributo;
* tipo de contenido;
* descripción cuando corresponda.

Ejemplos:

"snake"

"DX"

"combat"

"weapon"

"blood"

La búsqueda debe poder utilizarse dentro del builder.

Considerar un shortcut:

Ctrl + K

o:

Cmd + K

La búsqueda debe ser extensible para soportar nuevos tipos de contenido.

==================================================

# 40.5.6 FILTERS

==================================================

Las listas grandes deben soportar filtros.

Los filtros deben poder combinarse.

Ejemplo:

Skills:

Attribute = DX

Category = Combat

Difficulty = Average

Cost <= 10

Los filtros deben ser declarativos cuando sea posible.

No crear lógica específica de UI para cada catálogo.

==================================================

# 40.5.7 SORTING

==================================================

Las listas deben permitir ordenar cuando corresponda.

Opciones posibles:

* Alphabetical A → Z
* Alphabetical Z → A
* Cost ascending
* Cost descending
* Level ascending
* Level descending
* Recently added
* Recently used
* Category

El orden por defecto debe ser coherente y documentado.

==================================================

# 40.5.8 FAVORITES

==================================================

Evaluar sistema de favoritos.

El usuario podría marcar elementos como favoritos.

Ejemplo:

Favorites:

* Broadsword
* Combat Reflexes
* Snake
* Roots

Los favoritos deben ser metadata del usuario y no alterar las reglas del contenido.

==================================================

# 40.5.9 RECENTLY USED

==================================================

Evaluar una sección:

Recently Used

para elementos utilizados recientemente.

Esto será especialmente útil cuando el catálogo tenga cientos o miles de entradas.

No duplicar contenido.

Guardar únicamente referencias/IDs cuando sea posible.

==================================================

# 40.5.10 TOOLTIPS

==================================================

Los conceptos que puedan resultar ambiguos deben tener explicaciones contextuales.

Ejemplo:

Basic Speed
[?]

Tooltip:

"Determines reaction speed and contributes to Dodge."

No llenar la interfaz de texto explicativo innecesario.

Utilizar:

* tooltips;
* popovers;
* help panels;

cuando sean apropiados.

Los tooltips deben ser accesibles mediante teclado y no depender exclusivamente de hover.

==================================================

# 40.5.11 QUICK GUIDE

==================================================

Crear eventualmente una guía rápida para nuevos usuarios.

Ejemplo:

1. Define your character.
2. Set attributes.
3. Add advantages and disadvantages.
4. Add skills.
5. Configure equipment.
6. Create your Hatsu.
7. Add creations.
8. Review your character.
9. Save/export.

La guía debe poder cerrarse.

No mostrarla permanentemente si el usuario ya la completó.

==================================================

# 40.5.12 CONTEXTUAL HELP

==================================================

Agregar eventualmente un sistema de:

"What is this?"

o:

"How does this work?"

Especialmente para:

* reglas complejas;
* características derivadas;
* Hatsu;
* restrictions;
* vows;
* Soul Link;
* Blood Ink;
* point calculations.

La explicación debe utilizar contenido original/parafraseado y no copiar material protegido.

==================================================

# 40.5.13 PLACEHOLDERS

==================================================

Los inputs deben tener placeholders útiles.

Ejemplos:

Character Name:

"e.g. Kurapika"

Player:

"e.g. Franco"

Description:

"Describe your character..."

Creation:

"Describe what this creation does..."

Los placeholders NO deben reemplazar labels.

Los inputs siempre deben tener labels accesibles.

==================================================

# 40.5.14 INPUT VALIDATION

==================================================

Aplicar validación consistente.

Validar:

* tipos;
* rangos;
* longitudes;
* formatos;
* caracteres cuando corresponda;
* valores numéricos;
* IDs;
* contenido estructurado.

Utilizar:

Schema validation

*

Domain validation

*

UI feedback.

No depender exclusivamente de regex.

Las regex deben utilizarse solamente cuando realmente solucionen un problema de formato.

No bloquear caracteres arbitrariamente sin una razón funcional.

==================================================

# 40.5.15 INLINE EDITING

==================================================

Cuando sea apropiado, permitir editar información directamente.

Ejemplo:

Character Name

[Specialist]

en lugar de obligar siempre a abrir un modal.

No sacrificar accesibilidad ni claridad.

==================================================

# 40.5.16 ADD ITEM PREVIEW

==================================================

Cuando agregar un elemento pueda tener consecuencias importantes, mostrar un preview.

Ejemplo:

Combat Reflexes

Cost: 15 points

Category: Combat

Prerequisites: None

Effects:
...

[Cancel]

[Add]

No utilizar confirmaciones innecesarias para acciones triviales.

==================================================

# 40.5.17 UNDO / REDO

==================================================

Implementar eventualmente un sistema consistente de:

Undo

Redo

Debe estar basado en cambios de estado del Character Builder.

No implementar Undo únicamente manipulando elementos visuales.

Shortcuts:

Ctrl + Z

Ctrl + Shift + Z

Cmd + Z

Cmd + Shift + Z

El sistema debe ser compatible con:

* autosave;
* versioning;
* persistence.

==================================================

# 40.5.18 CHANGE HISTORY

==================================================

Preparar la arquitectura para historial de cambios.

Ejemplo:

03:42 — Added Snake

03:41 — Increased DX 12 → 13

03:40 — Added Combat Reflexes

03:38 — Changed character name

No es obligatorio implementar una UI completa inicialmente.

El modelo no debe impedir agregar esta funcionalidad posteriormente.

==================================================

# 40.5.19 CHARACTER DUPLICATION

==================================================

Permitir eventualmente:

Duplicate Character

Ejemplo:

Specialist v1

↓

Specialist v2

El personaje duplicado debe ser independiente.

Modificar uno no debe modificar el otro.

==================================================

# 40.5.20 TEMPLATES

==================================================

Preparar soporte para templates.

Ejemplos:

* Empty Character
* Beginner
* Combat Specialist
* Nen User
* Living Creations Specialist

Un template debe ser una definición reutilizable.

No acoplar templates a componentes específicos.

==================================================

# 40.5.21 CHARACTER STATES

==================================================

El builder debe representar claramente su estado.

Ejemplos:

✓ Valid

⚠ Warnings

✕ Errors

● In Progress

○ Incomplete

Cada sección puede mostrar su propio estado.

Ejemplo:

Identity ✓

Attributes ✓

Advantages ⚠

Skills ✓

Hatsu ✕

Creations ○

El usuario debe poder navegar directamente hacia los problemas.

==================================================

# 40.5.22 PERSISTENCE FEEDBACK

==================================================

Como el sistema tendrá autosave, mostrar claramente el estado.

Ejemplos:

Saving...

Saved

Saved 5 seconds ago

Save failed

No generar falsa sensación de persistencia.

Si un save falla:

* informar al usuario;
* mantener el estado local cuando sea posible;
* permitir retry.

==================================================

# 40.5.23 SESSION RECOVERY

==================================================

Si el usuario vuelve a la aplicación y existe un personaje local no finalizado:

mostrar:

"We found an unfinished character."

Opciones:

Restore

Discard

La recuperación no debe sobrescribir silenciosamente un personaje existente.

==================================================

# 40.5.24 EXPLAINABLE CALCULATIONS

==================================================

El Rules Engine debe poder proporcionar información suficiente para explicar cálculos importantes.

No devolver únicamente:

value: 10

Cuando sea útil devolver:

value: 10

breakdown:

* base: 9
* modifier: +1
* source: Combat Reflexes

Esto permitirá a la UI mostrar:

Why is my Dodge 10?

o:

Why does this cost 20 points?

El dominio debe seguir siendo independiente de la UI.

==================================================

# 40.5.25 POINT BREAKDOWN UI

==================================================

Mostrar claramente el coste de cada elemento.

Ejemplo:

ST 12

Cost:

+20 points

Y permitir eventualmente expandir:

Base: 10

Additional levels: +10

Total: 20

Lo mismo debe aplicarse a:

* advantages;
* disadvantages;
* skills;
* languages;
* equipment;
* other point-based systems.

# 40.5.26 CHARACTER POINT SUMMARY

==================================================

Remaining

# 40.5.27 MODIFIER BREAKDOWN

==================================================

Las características derivadas deben poder explicar sus modificadores.

Ejemplo:

Total: 10

==================================================

# 40.5.28 DEPENDENCY NAVIGATION

==================================================

Cuando una regla falle debido a una dependencia:

mostrar claramente cuál falta.

Ejemplo:

Broadsword 12+

[Go to Skills]

La UI debe permitir navegar directamente al lugar donde puede solucionarse el problema cuando sea posible.

==================================================

# 40.5.29 SMART VALIDATION

==================================================

La validación debe ejecutarse en tiempo razonable durante la edición.

No esperar únicamente al submit.

Diferenciar:

ERROR

WARNING

INFO

Ejemplo:

ERROR:

Character exceeds point budget.

WARNING:

Character has no equipment.

INFO:

Hatsu has no optional restrictions.

Los warnings no deben bloquear un personaje salvo que una regla explícitamente los defina como bloqueantes.

==================================================

# 40.5.30 ERROR EXPLANATIONS

==================================================

Los errores deben ser accionables.

Evitar:

INVALID_SKILL

POINT_ERROR

RULE_FAILED

Preferir:

"Broadsword requires DX 10 or higher. Current DX: 9."

Cuando sea posible incluir acciones:

[Increase DX]

[View Rule]

[Remove Skill]

Los códigos internos de error deben mantenerse separados del texto mostrado al usuario.

# 40.5.39 VIEW MODE / EDIT MODE

==================================================

# 40.5.41 INTERNATIONALIZATION

==================================================

Preparar internacionalización desde la arquitectura.

English

"Broadsword"

# 40.5.47 USER CONFIDENCE

==================================================

La interfaz debe comunicar claramente:

* cuándo se guardaron los datos;
* cuánto cuestan las cosas;

La aplicación debe evitar estados ambiguos.

El usuario nunca debería preguntarse:

"¿Se guardó?"

"¿Por qué cuesta esto?"

"¿Por qué no puedo agregarlo?"

"¿Qué está mal?"

si la aplicación puede proporcionar esa información.
